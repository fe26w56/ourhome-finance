# Documentation Structure

このディレクトリは、プロジェクトの各種ドキュメントを目的別に整理しています。

## ディレクトリ構成

```
docs/
├── features/           # 機能開発ドキュメント
├── architecture/       # アーキテクチャ・設計思想
├── supabase/          # データベース・バックエンド
├── troubleshooting/   # トラブルシューティング
└── setup/             # セットアップ・チェックリスト
```

---

## 📁 各ディレクトリの用途

### `features/`

**用途:** 機能ごとの開発ドキュメント（要件定義→設計→実装計画）

**命名規則:** `features/<feature-name>/`

**必須ファイル構成:**
```
features/<feature-name>/
├── requirements.md      # 要件定義（01-フェーズ）
├── design.md           # 設計書（02-フェーズ）
└── implementation.md   # 実装計画（03-フェーズ）
```

**ルール:**
- 新機能開発時は必ず `features/` 配下に新しいフォルダを作成
- ウォーターフォール形式（要件→設計→実装）に従う
- 各ファイル内では、前段階のドキュメントを相対パス（例: `requirements.md`）で参照
- 機能名は kebab-case で命名（例: `settlement-history-link`, `calendar-update`）

**参照方法の例:**
```markdown
<!-- design.md 内 -->
参照: `requirements.md`

<!-- implementation.md 内 -->
参照: `design.md`
```

---

### `architecture/`

**用途:** システム全体のアーキテクチャ、設計思想、技術仕様

**対象:**
- データスキーマ
- 状態管理設計
- API設計
- 認証設計
- 同期戦略
- 画面遷移・データフロー

**ルール:**
- システム全体に影響する設計変更は、既存ファイルを更新
- 新しいアーキテクチャ領域が追加される場合は、連番ファイルとして追加
- 機能固有の設計は `features/` に配置し、ここには含めない

---

### `supabase/`

**用途:** Supabase（データベース・バックエンド）関連のSQL、マイグレーション、変更履歴

**構成:**
```
supabase/
├── setup/           # 初期セットアップSQL
├── migrations/      # データマイグレーション
├── fixes/          # 修正用SQL
├── utils/          # 診断・確認用SQL
├── CHANGELOG.md    # 変更履歴
└── README.md       # Supabaseドキュメント
```

**ルール:**
- データベーススキーマ変更は必ず記録
- 本番適用前に `setup/` または `migrations/` に配置
- 修正用SQLは `fixes/` に配置
- 変更内容は `CHANGELOG.md` に記録

---

### `troubleshooting/`

**用途:** バグ調査、トラブルシューティング、デバッグ記録

**命名規則:** 内容を表す kebab-case（例: `user-creation-bug.md`, `oauth-debug.md`）

**記載内容:**
- 問題の症状
- 原因調査プロセス
- 根本原因
- 解決策
- 再発防止策

**ルール:**
- 重大なバグや長時間の調査が必要だった問題は必ず記録
- 解決後も削除せず、ナレッジとして保管
- 類似問題の参考資料として活用

---

### `setup/`

**用途:** 環境セットアップ、チェックリスト、初期設定手順

**命名規則:** `<system>-setup.md`, `<system>-checklist.md`

**ルール:**
- 新規メンバーのオンボーディングに使用
- 環境構築手順は最新の状態に保つ
- チェックリストは完了項目を明記

## 🔄 ワークフロー統合

このドキュメント構造は、プロジェクトの **適応型開発ワークフロー** と連携しています。

### 新機能開発時（`[NEW]` モード）

1. **要件定義（Phase 1）**
   - `features/<feature-name>/requirements.md` を作成
   - 機能の範囲、要件、成功基準を定義

2. **設計（Phase 2）**
   - `features/<feature-name>/design.md` を作成
   - `requirements.md` を参照し、アーキテクチャ・モジュール設計

3. **実装計画（Phase 3）**
   - `features/<feature-name>/implementation.md` を作成
   - `design.md` を参照し、実装ステップを詳細化

4. **実装と検証（Phase 4）**
   - 計画に従って実装
   - 完了後もドキュメントは保持（履歴として）

### バグ修正時（`[fix]` モード）

- 軽微な修正: ドキュメント不要
- 複雑なバグ: `troubleshooting/<issue-name>.md` を作成し、調査記録を残す

## 📝 ドキュメント作成ルール

### 必須項目

1. **タイトル（h1）**: 何のドキュメントか明確に
2. **概要セクション**: ドキュメントの目的を1-2文で
3. **参照**: 依存する他のドキュメントを明記
4. **日付**: 作成日・更新日（調査系ドキュメントの場合）

### 推奨事項

- 技術用語は一貫して使用
- コードスニペットは具体的に（ファイルパス、行番号を含める）
- 図解が有効な場合は Mermaid や画像を活用
- 曖昧な表現を避け、決定事項を明確に

---

## 🗂️ 既存ドキュメントの扱い

### 完了した機能のドキュメント

- **削除しない**: 履歴として保持
- **更新が必要な場合**: 既存ファイルを編集し、変更履歴をコミットメッセージに記載

### 古いトラブルシューティング

- **削除しない**: 類似問題の参考として価値がある
- **解決済みを明記**: ドキュメント冒頭に「✅ 解決済み（YYYY-MM-DD）」を追記
